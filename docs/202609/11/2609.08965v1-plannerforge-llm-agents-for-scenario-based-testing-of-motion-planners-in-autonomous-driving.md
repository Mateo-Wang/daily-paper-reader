## 摘要
确保自动驾驶的安全性是一项关键挑战。基于场景的测试是用于验证自动驾驶系统（ADS）的系统化流程，但它仍是一个碎片化的模块化流水线，其中场景生成、检索、修改、ADS执行和结果分析由彼此独立且交互很少的工具完成。大型语言模型（LLM）智能体已在ADS的感知、规划和控制等子系统展现出前景。然而，此前尚无工作以统一的LLM智能体框架覆盖ADS的整个基于场景的测试流水线。我们提出PlannerForge，一个LLM智能体框架，它扩展了所有基于场景的测试阶段（从场景生成到ADS评估），并新增了两个LLM增强阶段：ADS增强和ADS基准测试。我们在5种提示条件下，使用10个现成LLM对PlannerForge在所有任务（生成、选择、修改、模块路由、规划器测试和增强）上进行了评估。各任务最佳得分范围为0.88至1.00，开源20-35B后端在大多数任务上与商业API相当。开源模型如Qwen3.6:35B在五项任务中的三项上与商业API相当。将模块端到端串联后，保留83%/78%的种子查询（商业/开源）。它在自然语言生成上优于Scenario Factory 2.0（Finkeldei et al., 2025）（200个中193个可执行 vs. 144个），并实现了92-96%的所请求城市、道路和车辆属性。它在排名第1的选择上优于BM25（Robertson and Zaragoza, 2009）（92.0% vs. 67.5%），并在物理有效编辑上优于From-Words-to-Collisions（Gao et al., 2025）（>=94% vs. 31%）。在N=400时，成本调优将规划器成功率从50.4%提升至70.2%，并将碰撞从19.0%降至8.4%，且无需领域特定微调。

## Abstract
Ensuring the safety of autonomous driving is a critical challenge. Scenario-based testing is a systematic process used to validate Autonomous Driving Systems (ADSs), but it remains a fragmented modular pipeline in which scenario generation, retrieval, modification, ADS execution, and results analysis are performed by separate tools with little interaction. Large Language Model (LLM) agents have shown promise across ADS sub-systems such as perception, planning, and control. However, no prior work covers the whole scenario-based testing pipeline for ADSs with a unified LLM-agent framework. We present PlannerForge, an LLM-agent framework that extends all scenario-based testing stages (from Scenario Generation to ADS Assessment) and adds two further LLM-enhanced stages: ADS Enhancement and ADS Benchmarking. We evaluate PlannerForge with 10 off-the-shelf LLMs across all tasks (Generation, Selection, Modification, Module Routing, Planner Testing, and Enhancement) under 5 prompt conditions. Best-per-task scores range from 0.88 to 1.00, and open-source 20-35B backends match commercial APIs on most tasks. Open-source models such as Qwen3.6:35B match commercial APIs on three of the five tasks. Chaining the modules end-to-end retains 83% / 78% of seed queries (commercial / open). It outperforms Scenario Factory 2.0 (Finkeldei et al., 2025) on natural-language generation (193 vs. 144 executable of 200) and realises 92-96% of requested city, road and vehicle attributes. It outperforms BM25 (Robertson and Zaragoza, 2009) at rank 1 selection (92.0% vs. 67.5%) and From-Words-to-Collisions (Gao et al., 2025) on physically valid edits (>=94% vs. 31%). At N=400, cost-tuning lifts planner success from 50.4% to 70.2% and cuts collisions from 19.0% to 8.4%, without domain-specific fine-tuning.

- **研究动机**：自动驾驶系统（ADS）向 SAE L4 迈进依赖严格验证，但真实道路测试稀有边缘案例成本极高，行业转向仿真中的"基于场景的测试"（scenario-based testing）。

- **研究缺口**：LLM 虽已在 ADS 的感知、规划、控制等子系统中展现潜力，但此前工作几乎只聚焦于"场景生成"这一单点，**尚无统一的 LLM 智能体框架覆盖整个场景化测试生命周期**。

## 2. 方法论

### 2.1 核心思想

- 将 LLM 驱动的场景化测试形式化为"**语言到结构化输出的决策序列**"：在每个对话轮次 t，智能体观察 $x_t = (u_t, s_t, \theta_t, h_t)$（用户话语、场景、规划器配置、对话历史），并输出符合 schema 的结构化产物。
- 关键设计：`f_gen`、`f_mod`、`f_tune` 均为**受约束生成器**（constrained generators），其输出必须满足预定义 XML/YAML/JSON schema——这正是核心语言挑战所在。

### 2.2 六大模块

- **生成模块（Generation）**：两阶段流水线。
  - 阶段 1：LLM 将自然语言解析为结构化 JSON 意图（地点、道路等级、交通密度、车辆构成、时长）→ 经 Overpass API 查询 OpenStreetMap → SUMO 微观仿真 → 转换为 CommonRoad 格式。
  - 阶段 2：用户选 ego 车与目标区域（LLM 可建议 ego 候选：首车/按类型/按索引），合成规划问题。
- **选择模块（Selection）**：五步对话式槽位提取，按四层元数据（location、tags、road_net、obstacles、velocity）做**单调剪枝**：$D^{(k)} = D^{(k-1)} \cap \text{match}(\hat{\ell}_k)$；若精确匹配为空则回退到 SentenceTransformer 语义检索。
- **模块路由（Module Router）**：意图分类器，动作集 $A = \{\text{MODIFY, TUNE, TEST, ANALYSE, QA}\}$；两阶段 LLM 函数调用（先识别模块并抽取参数，再由 Process Engine 分发）。
- **修改模块（Modification）**：经 CommonRoad–SUMO 接口，支持四类编辑——轨迹重定向（T）、行为预设（B，六种跟驰预设）、车辆增删（P）、目标区域编辑（G）。
- **测试与增强（Testing & Enhancement）**：统一执行接口 $\pi_P(s,\theta) = (\tau, c, m)$（轨迹、碰撞标志、成本日志）；调参器 `f_tune` 将定性预设或显式权重调整转为 schema 合规的 YAML 覆盖。
- **分析模块（Analysis）**：基于四类上下文块（批量统计、逐场景日志、当前配置、CSV 路径）生成自然语言诊断与调参建议，闭合与调参器的回路。

### 2.3 提示技术

- **上下文提示（CP）**：注入输出 schema、语法约束与可用算子。
- **思维链（CoT）**：将生成拆解为显式推理步骤。
- **上下文学习（ICL）**：添加正例与负例（拒绝示例）。
- 五种提示条件构成阶梯：`baseline` → `cp` → `cp_cot` → `cp_icl` → `cp_icl_cot`。

### 2.4 技术栈

- 前端 Gradio，后端 LangChain，三层状态管理（对话记忆、UI 历史、会话状态）。
- ChromaDB 向量库索引 500+ CommonRoad 场景，SentenceTransformer 嵌入。
- 集成两款规划器：采样式 **Frenetix** 与学习式 **MP-RBFN**。

- **模块级性能**：各任务最佳得分 0.88（选择）至 1.00（规划器测试）；生成 0.957、路由 0.997、修改标题检查近 100%。
- **开源 vs 商业**：开源 20–35B 模型在多数任务上媲美商业 API，Qwen3.6:35B 在五项任务中的三项上持平。
- **端到端**：链式流水线保留 83%（商业）/ 78%（开源）种子查询；选择与修改是主要泄漏点。
- **生成对比**：193/200 可执行（vs SF 2.0 的 144/200），实现 92–96% 请求属性，产出 7 类交通参与者（vs 4 类），诱发 3.3 倍规划器碰撞。
- **选择对比**：Rank-1 满意度 92.0%（vs BM25 的 67.5%），Any@5 为 96.5%（vs 86.0%）。
- **修改对比**：物理有效编辑 ≥94%（vs FWtC 的 31%），参与者与目标编辑对规划器压力更大。
- **增强效果**：N=400 时成功率 50.4%→70.2%，碰撞 19.0%→8.4%，无需领域微调。
- **三条可迁移洞见**：
  - 提示技术应对不同失败模式（CP 饱和封闭词表，ICL 处理拒绝，CoT 处理联合约束）。
  - 外部 CoT 与原生推理冲突（对推理型模型加 CoT 反而降低 sat_all）。
  - 可靠性需要可执行验证框架（解析、schema 校验、下游执行）。

## 7. 优点

- **首创性**：首个覆盖 ADS 场景化测试全生命周期的统一 LLM 智能体框架，并扩展出增强与基准测试两个新阶段。
- **架构设计**：
  - 模块路由器打破传统线性流程，实现灵活的后选择导航。
  - 受约束生成器 + 幻觉隔离设计（LLM 从不直接输出地图几何、拓扑或轨迹，从结构上排除三类幻觉）。
  - 统一 $\pi_P$ 接口支持跨规划器（Frenetix / MP-RBFN）对比。
- **工程可靠性**：每个计分模块都经过解析、schema 校验、执行验证，"提示提高命中率，验证框架保证可靠性"。
- **可复现性**：固定模型 ID 与 Ollama 镜像标签；代码与数据开源；提供完整提示文件。
- **对比严谨**：在每阶段均与最强可用基线对比，且给予基线原生输入以保公平。
- **实用洞察**：量化了提示技术与失败模式的匹配关系，指出开源 20–35B 模型的可行性，为低成本验证提供路径。

## 8. 不足与局限

- **开环限制**：其他交通参与者仅按记录轨迹或 SUMO 导出轨迹运动，**不对 ego

的动态行为做出反应**，缺乏真正的闭环交互。这意味着"安全关键性"主要来自初始条件的构造，而非多智能体博弈，可能低估真实交通中对抗性/协同性行为带来的风险。
- **分析模块缺乏客观评测**：分析模块生成的诊断与调参建议未与 ground truth 对照评分，只有定性示例，无法量化其正确率，是整篇论文中唯一没有程序化答案键的模块。
- **数据不完整**：部分开源模型（think/no-think 变体）在投稿时仍处采集阶段，表中标 N/A，承诺 camera-ready 补齐；这意味着开源 vs 商业的结论目前只建立在部分子集上，统计效力受限。
- **场景与仿真器生态绑定**：整条流水线强依赖 OpenStreetMap → SUMO → CommonRoad 工具链，未验证迁移到 CARLA、CARLA ScenarioRunner、nuPlan、Waymo Open Sim Agents 等生态的可行性；ChromaDB 中仅 500+ 场景，地理与场景类型分布存在偏置。
- **语言与地域覆盖**：查询语料为英文（15 个国家代码指场景来源而非语言），未评估多语言或本地化表述下的鲁棒性。
- **规划器覆盖面窄**：仅集成 Frenetix（采样）与 MP-RBFN（学习式）两款规划器，二者均为相对轻量的研究原型，未涉及工业级 ADS 栈或端到端神经网络规划器，跨规划器结论的外推需谨慎。
- **安全指标单一**：以碰撞标志 c 作为安全代理，未纳入近失（near-miss）、TTC/PET、舒适度、法规合规等更细粒度的风险度量；"诱发 3.3 倍碰撞"这类结论对指标定义敏感。
- **LLM 非确定性处理不足**：除成本调优实验做了 3 轮独立重复外，主实验未报告多次运行的方差或置信区间，跨模型 0.997 vs 0.996 这类微小差距可能落在噪声内。
- **提示工程可能过拟合**：五种提示条件在 10 个模型上取最优，存在对 benchmark 的隐式调优风险；论文未提供留出集或跨 benchmark 迁移验证。
- **缺乏人类用户研究**：作为"聊天机器人驱动"的交互式框架，未开展测试工程师可用性实验（任务完成时间、认知负荷、信任度），而人机交互恰是其核心卖点之一。
- **成本未充分量化**：端到端 ≈126 s/99 s、≈42.5k/32.6k tokens 为均值，但未给出总 API 费用、与规则式流水线（SF 2.0）的端到端时间/成本对比，也未讨论大规模回归测试下的经济可行性。
- **无覆盖度保证**：选择与生成均为"按需检索/构造"，不提供形式化覆盖准则（如场景空间覆盖率、组合覆盖），与工业界对可度量验证充分性的需求仍有距离。

## 9. 可迁移启示与未来方向

- **架构层面的可迁移性**：
  - "**受约束生成器 + schema 校验 + 下游执行验证**"三段式，是把 LLM 接入任何安全攸关工程流水线的通用范式，可迁移至机器人、航空、电力系统等需要结构化产物的测试域。
  - "**LLM 不直接产出几何/拓扑/轨迹**"的幻觉隔离原则，为高风险场景下划定 LLM 职责边界提供了可复用的设计准则。
  - 模块路由器将线性流水线改为意图驱动的可跳转图，这一模式对任何多阶段工具链（数据标注、CI/CD、EDA 流程）都有借鉴意义。
- **方法层面的可迁移性**：
  - 提示技术与失败模式的对应关系（CP 封闭词表饱和 / ICL 处理拒绝样本 / CoT 处理联合约束）具有跨任务普适性。
  - "外部 CoT 与原生推理冲突"这一发现对当下推理型模型的提示设计有直接警示价值：**对已具备原生思维链的模型不应再叠加显式 CoT**。
- **可能的研究延伸**：
  - 闭环化：让其他交通参与者由 LLM 或学习式行为模型驱动并对 ego 反应，把开环场景升级为交互式对抗场景生成。
  - 覆盖度引导：将场景选择与生成接入覆盖度指标（组合覆盖、边界覆盖），形成"覆盖驱动 + LLM 构造"的混合闭环。
  - 成本-可靠性权衡：研究小模型专职分工（路由用小模型、生成用大模型）的级联架构，降低 80k 调用级别的开销。
  - 人类在环：引入测试工程师反馈，把分析模块的诊断建议纳入偏好优化或人工评分基准。

## 10. 总体评价

- **贡献定位**：PlannerForge 的主要价值不在单点算法创新，而在于**系统性地把 LLM 智能体从"场景生成器"提升为"测试生命周期编排器"**，并给出了可运行、可复现、可扩展的工程实现与大规模实证。
- **证据强度**：8 个任务切片 × 10 个模型 × 5 种提示条件的网格化评测、每模块配备最强可用基线、程序化答案键评分、约 80k 次调用与端到端链式验证，使其结论具有较强的经验支撑，明显超出该领域常见的演示型工作。
- **结论可信度**：模块级最优 0.88–1.00、开源 20–35B 媲美商业 API、端到端保留 78–83%、规划器调参把成功率从 50.4% 提升到 70.2% 等结论，方向一致且量级合理；但分析模块缺客观评分、开环设定、单指标安全度量与部分数据缺失，是需要打折看待的三处软肋。
- **实践意义**：对 ADS 验证团队而言，该工作提示了一条现实路径——用现成开源模型 + 强约束 + 执行验证，即可在无需领域微调的前提下把高度碎片化的测试流水线统一为一个对话式入口，其工程范式价值大于其具体数值结果。
- **一句话总结**：PlannerForge 证明了"受约束的 LLM 智能体 + 可执行验证框架"能够端到端接管场景化 ADS 测试的全生命周期，在覆盖广度与基线对比上表现扎实，但其开环场景、单一安全指标与缺失的用户/分析模块评测，仍是走向工业级可度量验证前必须补齐的环节。
